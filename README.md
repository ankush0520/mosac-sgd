# MOSAC-SGD

**M**ulti-view **O**verlapping **S**pammer-group detection with **A**ggregated **C**oordination signals.
Unsupervised detection of collusive review-spammer groups whose members write LLM-generated text and
take part in several overlapping campaigns. This repository is the complete, runnable implementation of
the end-semester report (`mosac_sgd_endsem.tex`): data pipeline, co-review graph, planted-campaign
benchmark, Stages 1–3, five baselines, and experiments E1–E6. Everything runs on a normal CPU laptop.

Measured numbers are in [`results/RESULTS.md`](results/RESULTS.md) (generated by the run, not typed by hand).

## 1. Datasets: what is used, where it comes from, access status

| Dataset | Role in this project | Source (downloaded by `src/download.py`) | Access / licence | Used? |
|---|---|---|---|---|
| **Amazon Reviews 2023 – Musical Instruments** (McAuley Lab) | primary host (real background reviews + text) for the planted-campaign benchmark | `huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023`, `raw/review_categories/Musical_Instruments.jsonl` (1.56 GB, 3.0 M reviews) | public, no login; released for research use by the McAuley Lab (see dataset card) | **yes** |
| **Amazon Reviews 2023 – All Beauty** | second host (cross-domain check) | same repository, `All_Beauty.jsonl` (327 MB, 0.70 M reviews) | as above | **yes** |
| **YelpChi** (Rayana & Akoglu 2015), CARE-GNN release | E6: real user-level spam labels (Yelp filter) | `github.com/YingtongDou/CARE-GNN`, `data/YelpChi.zip` | public on GitHub (repo licence Apache-2.0; underlying data from Rayana & Akoglu, research use) | **yes** (behaviour only: the release has no raw text or timestamps) |
| **Amazon (CARE-GNN)** (Zhang et al. 2020, Musical Instruments users) | E6: real user-level labels (helpful-vote based) | same repository, `data/Amazon.zip` | as above | **yes** (behaviour only) |
| **OpSpam v1.4** (Ott et al. 2011) | sanity check for the text encoder | `myleott.com/op_spam_v1.4.zip` | public; CC BY-NC-SA 3.0 | **yes** |
| Yelp Open Dataset | was the planned primary host | `business.yelp.com/data/resources/open-dataset/` | requires accepting Yelp's terms in a browser, so it **cannot be script-downloaded**; it also has **no spam labels** | **no** (supported if you place the file manually, see §5) |
| YelpNYC / YelpZip (raw, with text) | real labels with text | authors, on request | not public | **no** |
| AmazonCPA (TKCCL) | — | no public source found | not public | **no** |

Nothing in the repository contains review text from these datasets except the synthetic LLM texts in
`data/llm_cache/` (see below). Raw and processed data live in `data/raw/`, `data/processed/` (git-ignored).

**Ground truth.** There are no public *group-level* spam labels. The main evaluation therefore uses a
*planted-group* benchmark: synthetic campaigns are injected into the real Amazon background with exact
ground truth (members, targets, window, overlaps), following the protocol in the report. E6 then checks
agreement with the only public real labels we could download (user-level, YelpChi / Amazon CARE-GNN),
and OpSpam checks the text encoder on real crowd-sourced deceptive reviews.

**LLM-written campaign text.** `data/llm_cache/<host>.jsonl` holds review texts generated once on CPU
with the open model **Qwen/Qwen2.5-0.5B-Instruct** (Apache-2.0) using the report's prompt template
(persona, aspects, length, rating). Pools: `T1` (one persona, fixed length/temperature), `T2` (varied
persona/length/temperature 0.7–1.1) per campaign brief, and `benign` (ordinary opinions with random
aspects, for the benign-LLM control). These files are committed so you do **not** need to run the LLM;
regenerate with `python scripts/generate_llm_texts.py --category Musical_Instruments`. All texts there
are synthetic.

## 2. Setup (CPU only, Windows / macOS / Linux)

```bash
conda create -n mosac python=3.11 -y && conda activate mosac      # or python -m venv .venv
pip install torch --index-url https://download.pytorch.org/whl/cpu  # CPU wheel, ~200 MB
pip install -r requirements.txt
```

## 3. One-command reproduction

```bash
python -m src.download          # ~1.9 GB download (Amazon-2023 x2, CARE-GNN, OpSpam)
python -m src.run               # all experiments; writes results/ and results/RESULTS.md
```

`python -m src.run --quick` does 2 seeds on the primary host only (a smoke run, ~10 min).
`python -m src.run --only E1 E3` runs a subset. The first run also downloads the SBERT model
`sentence-transformers/all-MiniLM-L6-v2` (90 MB) from Hugging Face and caches embeddings in `data/cache/`.

## 5. Deviations from the report, and why

Everything below is also visible in the code and configs. Where the report gave a value, the default
config keeps it unless a line here says otherwise.

1. **Hosts.** The report planned Yelp Open Dataset + Amazon-2023. Yelp can't be fetched by script and has
   no labels, so both hosts are Amazon-2023 categories (Musical Instruments 2019–2020 with users ≥ 3 /
   items ≥ 10 reviews; All Beauty with a relaxed 2 / 5 filter because it is very sparse). Yelp still loads
   if you place the file manually (`hosts: Yelp` in the config).
2. **Generator LLM.** Qwen2.5-0.5B-Instruct on CPU (laptop constraint). Cache sizes (after trimming the
   budget so generation fits in ~2 h of CPU): Musical Instruments 25 briefs × (24 T1 + ~16 T2) + 400
   benign = 1,478 texts; All Beauty 12 briefs × (16 T1 + ~12 T2) + 300 benign = 641 texts. Campaigns
   draw a brief at random (with replacement) and each member keeps one text for all of its targets.
   When a campaign has more members than texts, texts repeat inside the campaign.
3. **Benign-LLM control volume.** `control_ratio: 0.5`: benign-LLM reviews = 0.5 × campaign reviews
   (~1.7k per instance), sampled with replacement from the benign pool.
4. **Co-review graph.** Adds the pilot's `min_common: 2` (a pair must co-review ≥ 2 items within the
   window). Without it the real background produces a dense, uninformative graph.
5. **Stage-2 encoders** are trained on the users that appear in at least one candidate group (not on all
   users). This keeps CPU time to seconds. Training: Adam, lr 1e-3, 200 full-batch epochs, τ = 0.2.
6. **h_g** uses PCA (16 dims) of the mean member vector, so the Mahalanobis covariance is well posed.
7. **Directional scorer (added).** The report's Mahalanobis / Isolation-Forest scorers are two-sided. On
   this benchmark planted campaigns make up a large share of candidate groups, so "unusual" ends up
   meaning the *small organic* groups (e.g. buyers of the same microphone bundle). Both scorers then rank
   real campaigns *low* (validation group F1 ≈ 0.03–0.36). The added `directional` scorer counts only
   deviations in the a-priori suspicious direction of the Mukherjee et al. (2012) group-spam indicators:
   size, shared items, short time window, rating extremity, and CS / AO / SP. The other features enter
   through a Mahalanobis term. This is still label-free. The choice between the three scorers, the
   overlapping algorithm and τ_g is made on the **validation injection only** (seed 100, see
   `results/_tune_*`). The directional scorer won on both hosts.
8. **Model selection.** `w_min` per algorithm is chosen by Stage-1 metrics on validation (as in the
   report). The algorithm / scorer / τ_g are then chosen by mean(group F1@k, user AUC-PR, MR) on the same
   validation instance. Test seeds 0–4 are never used for any choice.
9. **Baselines are "-lite" re-implementations** (as the report says). SC-Com-lite is the only supervised
   one (Random Forest trained on the validation injection's labels).
10. **E6** uses the CARE-GNN releases, which have no text or timestamps. So only the behavioural pipeline
    runs, and the co-review graph is rebuilt from their relations (YelpChi: R-T-R ∧ R-S-R between users
    recovered from R-U-R; Amazon: U-P-U ∧ U-S-U).
11. **Scale.** About 57k reviews (primary host) per instance, 5 seeds, 2 hosts. The full `python -m src.run`
    took **≈ 51 min** on a 4-core CPU without GPU (tuning ≈ 7 min, E1 7.5, E2 4.7, E3 13.7, E4 2.3, E5 13.8,
    E6 1.6). The one-off SBERT embedding of all texts adds ~5 min on the first run.


## 6. Results summary

Full tables: [`results/RESULTS.md`](results/RESULTS.md). Mean ± std over 5 test seeds; k = 30 groups,
k = #spammers for users. Settings: T2 LLM-diverse text, benign-LLM control on, 25 % overlap.

**E1 – main comparison, group F1@30 / user AUC-PR**

| Method | Musical Instruments | All Beauty |
|---|---|---|
| Behavioural IF (no graph) | – / 0.447 | – / 0.551 |
| SC-Com-lite (supervised) | 0.247 / 0.573 | 0.372 / 0.679 |
| TKCCL-lite | 0.301 / 0.310 | 0.312 / 0.349 |
| OSG-behav. (Ego-Splitting, no text) | **0.720** / **0.941** | **0.646** / **0.914** |
| Text-only | 0.400 / 0.796 | 0.267 / 0.704 |
| **MOSAC-SGD** (DEMON + fused + directional + noisy-OR) | **0.720** / 0.937 | 0.556 / 0.883 |

MOSAC-SGD ties the strongest baseline on the primary host. On All Beauty it is behind the
behaviour-only overlapping baseline (Wilcoxon p = 0.0625, the minimum possible with 5 seeds). It beats
the disjoint and temporal baselines by a wide margin on both hosts.

**E2 / RQ1 – does text help? (group F1@30, primary host)**

| | T0 templated | T1 LLM-plain | T2 LLM-diverse |
|---|---|---|---|
| Behaviour-only | 0.74 | 0.74 | 0.74 |
| Text-only (ctrl off / on) | 0.72 / 0.72 | 0.57 / 0.57 | 0.39 / 0.40 |
| Fused (ctrl off / on) | **0.84 / 0.84** | **0.79 / 0.80** | 0.69 / 0.72 |

H1 is **partly supported**. Fusing text helps for templated and single-persona LLM campaigns (+0.10 and
+0.06 F1). It does **not** help for diverse LLM campaigns with the control on (0.72 vs 0.74). Text-only
does not drop when the control is switched on. This shows that CS / AO / SP measure coordination, not
"AI style". The flip side is that diverse LLM text hides most of that coordination.

**E3 / RQ2 – overlapping membership (30 % overlap)**

| Grouping | MR | MMR | user R@k on multi-campaign spammers |
|---|---|---|---|
| Louvain (disjoint) | 0.20 | 0.00 | 0.59 |
| Ego-Splitting (OSG-behav.) | 0.90 | 0.91 | 0.99 |
| BigCLAM | **0.97** | **0.97** | 0.97 |
| DEMON (selected) | 0.85 | 0.84 | **1.00** |

H2 is **supported**. Every overlapping method recovers 4× more (spammer, campaign) memberships than
disjoint grouping, and multi-campaign recall rises from 0.59 to 0.97–1.00. User P@k rises too
(0.54 → 0.92). The propagation rule (noisy-OR / max / mean) changes AUC-PR by less than 0.01.

**E4 – ablations.** The largest drops come from removing overlap (−0.47 F1) and removing the
behavioural branch (−0.23). Removing the text features costs −0.05. Two "removals" *help*: SVD instead of
GraphSAGE (+0.08) and plain concatenation instead of InfoNCE (+0.03). So the learned contrastive
embedding adds nothing measurable at this scale.

**E5 – robustness.** Harder campaigns (5–30 day window, 60 % target hit rate) drop F1 to 0.60 and
AUC-PR to 0.80. With only K = 10 campaigns, F1 is 0.17: with few planted groups, organic groups dominate
the top-30. The method is sensitive to `w_min` (0.6 would have scored 0.87 on test, but validation picked
0.05). Runtime is dominated by SBERT embedding; graph + Stages 1–3 take < 7 s per instance.

**E6 – real labels (behaviour only).** On YelpChi and the CARE-GNN Amazon set, the group pipeline does
**not** beat a user-level Isolation Forest. Best group variant vs IF, AUC-PR: 0.30 vs 0.37 on YelpChi and 0.15 vs 0.24 on Amazon.
These labels are individual filtered or low-helpfulness reviewers, not collusion groups. Most labelled
users are not in any co-review group, so this is weak evidence either way. It is reported as is.

**OpSpam text sanity check.** SBERT + logistic regression separates deceptive from truthful hotel
reviews with 77.6 % ± 0.7 % 5-fold accuracy, so the text encoder carries a usable signal.
